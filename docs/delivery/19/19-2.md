# 19-2 Add min_stake_amount field to StorageMetrics and restructure QueryMetricsResponse

[Back to task list](./19-tasks.md) | [View Backlog](../backlog.md#user-content-19)

## Analysis
- **Purpose:** Add min_stake_amount to StorageMetrics and restructure QueryMetricsResponse to embed fields directly including current_stake_amount from staking module.
- **Non-functional Considerations:**
  - Security: Fields must be properly calculated and not manipulable by users
  - Performance: Staking queries add overhead but should be acceptable for metrics queries
  - Observability: Users can compare their current stake vs required stake in single query
- **Business Rules:**
  - min_stake_amount = total_bytes × storage_stake_multiple (added to StorageMetrics)
  - current_stake_amount = sum of all delegations from staking module (only in QueryMetricsResponse)
  - QueryMetricsResponse embeds fields directly instead of nested StorageMetrics
  - All amounts should be in udys as string representation
  - Calculation must use cosmos-sdk decimal precision

## Design
- **Technical Specifications:**
  - Add `min_stake_amount` field to `StorageMetrics` message in `proto/dysonprotocol/storage/v1/storage.proto`
  - Restructure `QueryMetricsResponse` in `proto/dysonprotocol/storage/v1/query.proto` to embed fields directly
  - Add `current_stake_amount` field only to `QueryMetricsResponse` (not StorageMetrics)
  - Field types: all `string` to store decimal amounts in udys
  - Update QueryMetrics implementation to query staking module and populate all fields
- **Architectural Compliance:**
  - Separates concerns: StorageMetrics for storage data, QueryMetricsResponse for query-specific data
  - QueryMetricsResponse provides complete view including both storage and staking information
  - Maintains clean separation between storage metrics and staking queries

## Testing
- **Test Cases:**
  - StorageMetrics serialization includes min_stake_amount field
  - QueryMetricsResponse has embedded fields: owner, total_bytes, min_stake_amount, current_stake_amount
  - min_stake_amount is calculated correctly for various scenarios
  - current_stake_amount is queried correctly from staking module
  - All fields are properly formatted as string representations of udys
  - Existing tests continue to pass after restructuring
- **Test Data Requirements:**
  - Test scenarios with different total_bytes values
  - Test scenarios with different storage_stake_multiple values
  - Test accounts with various delegation amounts for current_stake_amount
  - Edge case: total_bytes = 0, storage_stake_multiple = "1.0"
  - Edge case: storage_stake_multiple = "0" (disabled)
  - Edge case: account with no delegations (current_stake_amount = "0")

## Change Plan
- **Files to Modify:**
  - `proto/dysonprotocol/storage/v1/storage.proto` - Add min_stake_amount field to StorageMetrics
  - `proto/dysonprotocol/storage/v1/query.proto` - Restructure QueryMetricsResponse to embed fields directly
  - `x/storage/keeper/grpc_query.go` - Update QueryMetrics implementation for new response structure
- **Implementation Approach:**
  1. Add min_stake_amount field to StorageMetrics protobuf definition
  2. Restructure QueryMetricsResponse to embed owner, total_bytes, min_stake_amount, current_stake_amount directly
  3. Run `make proto-gen install` to generate Go code
  4. Update QueryMetrics implementation to:
     - Calculate min_stake_amount using storage metrics
     - Query current_stake_amount from staking module
     - Populate all fields directly in response
  5. Update tests to verify new response structure and all field calculations
