# 11-5 Implement chain_logic callbacks for queue operations

[Back to task list](./tasks.md) · [View Backlog](../backlog.md#user-content-11)

## Analysis

- **Purpose:** Add on_queue_message and on_queue_response callbacks to L1 and L2 classes, enabling them to handle queue events.
- **Non-functional Considerations:**
  - Security: Callbacks must validate queue message data before processing
  - Performance: Callbacks should execute efficiently during queue processing
  - Observability: Callback execution results should be logged for debugging
- **Business Rules:**
  1. L1 and L2 classes must implement on_queue_message and on_queue_response callbacks
  2. Callbacks are invoked during automatic queue processing in on_begin_block
  3. Callback failures are logged but do not fail queue processing or block execution
  4. Callbacks receive validated queue message/response data
  
- **Architectural Constraints:**
  1. **Storage Isolation:** L2 can never write to L1 storage, and L1 can never write to L2 storage
  2. **L1 reads L2:** L1 can only read the latest stored checkpointed block of L2 that anyone may have stored with a dyson tx
  3. **L2 reads L1:** L2 can always read the latest L1 storage with a _query, because it is running in a query on the dysond node
  4. **Asynchronous Blocks:** There will be many indeterminate blocks between either chain, we cannot assume each block happens regularly
  5. **L2 State Collection:** When running the L2 query ScriptRun, use the `--extra-code` flag to include extra code in the query to monkey patch _msg or make a _l2_store function that collects and outputs the new state and block

## Design

- **Technical Specifications:**
  - L1 and L2 classes already have callbacks, just need to invoke them:
    ```python
    # L2 class callbacks (already implemented)
    chain_scope["chain_callbacks"] = {
        "on_begin_block": l2.on_begin_block,
        "on_tx": l2.on_tx,
        "on_end_block": l2.on_end_block,
        "on_queue_message": l2.on_queue_message,
        "on_queue_response": l2.on_queue_response,
    }
    ```
  - Process flow clarification:
    1. **L1 public function** (e.g., `say_hi()`) calls L1 instance method
    2. **L1 instance** queues message via `send_message()`
    3. **L2 instance** processes message via `on_message()` and returns response
    4. **L1 instance** receives response via `on_response()` and stores it
  - No separate chain_logic string needed - L2 instance methods serve as callbacks

- **Architectural Compliance:**
  - All logic encapsulated in L1 and L2 classes
  - L1 state persisted in DysonProtocol storage
  - L2 state maintained in memory (tests) or TEW block state (production)
  - Communication via queue system with proper message/response handling

## Addendum: Architecture Simplification (2025-01-02)

The implementation has evolved from the original design. The chain_logic callbacks have been integrated directly into the script:

### Key Changes:
1. **No chain_logic validation**: There is no separate chain_logic code to validate for callbacks
2. **Direct implementation**: The callbacks (`on_queue_message`, `on_queue_response`) are now methods of the L1 and L2 classes
3. **No chain_callbacks dictionary**: The callbacks are invoked directly from the queue processing logic
4. **Simplified architecture**: All logic is contained within `queue_chain.py`

### Updated Implementation:
```python
# Callbacks are now methods of L1/L2 classes
class L1(Queueable):
    def on_message(self, message: Message):
        """Process messages from L2"""
        # Handle message directly
        
class L2(Queueable):
    def on_message(self, message: Message):
        """Process messages from L1"""
        # Handle message directly
```

### Process Flow (Unchanged):
1. **L1 public function** (e.g., `say_hi()`) calls L1 instance method
2. **L1 instance** queues message via `send_message()`
3. **L2 instance** processes message via `on_message()` and returns response
4. **L1 instance** receives response and stores it

The architectural constraints and business rules remain the same, but the implementation is now more direct without the intermediate chain_logic layer.
