# 18-3 Implement metrics tracking in msg_server.go

[Back to task list](./18-tasks.md) | [View Backlog](../backlog.md#user-content-18)

## Analysis

- **Purpose:** Modify StorageSet and StorageDelete message handlers to automatically update storage metrics when storage entries are created, updated, or deleted.
- **Non-functional Considerations:**
  - Security: Metrics updates must be atomic with storage operations
  - Performance: Minimal overhead added to existing storage operations
  - Observability: Metrics must accurately reflect current storage state at all times
- **Business Rules:**
  - StorageSet: Add new data size to metrics, subtract old data size if updating existing entry
  - StorageDelete: Subtract deleted data sizes from metrics
  - Metrics must never go negative (handle edge cases gracefully)
  - All metrics updates must be transactional with storage changes

## Design

- **Technical Specifications:**
  - Modify `StorageSet` method to update metrics when setting/updating entries
  - Modify `StorageDelete` method to update metrics when deleting entries
  - Use keeper methods for metrics management (to be created in task 18-4)
  - Ensure metrics updates are atomic with storage operations
- **Architectural Compliance:**
  - Maintains existing message handler patterns
  - Uses keeper abstraction for state management
  - Preserves existing error handling and validation logic

## Testing

- **Test Cases:**
  - Setting new entry increases metrics by data size
  - Updating existing entry adjusts metrics by size difference
  - Deleting entries decreases metrics by deleted data sizes
  - Failed operations do not update metrics
  - Metrics remain consistent across operations
- **Test Data Requirements:**
  - Storage entries of various sizes for testing metric calculations
  - Scenarios with multiple operations per address

## Change Plan

- **Files to Modify:**
  - `x/storage/keeper/msg_server.go`
- **Implementation Approach:**
  - Add metrics update logic to StorageSet after successful storage operation
  - Add metrics update logic to StorageDelete after successful deletion
  - Handle edge cases where metrics operations might fail
  - Ensure no disruption to existing storage functionality
